# Further Rust import stages

The direction is to move substantial import pipelines into Rust, so JavaScript makes one call per batch or operation. The current batch Source validator/persister establishes that boundary. The user authorized broader conversion wherever it helps, with an eventual Rust implementation as the direction. All work continues from `rust-object-import`; preserve the original `rust` branch.

1. **Batch decompression for metadata objects.** The mutable-heavy command still sends Versions/components/histories through native classification and then Node inflation/parsing. Extend the native batch result to carry bounded inflated metadata, retaining canonical Node model hydration initially. This removes per-object zlib callbacks and duplicate inflation. Preserve byte decoding, malformed-JSON/error behavior, external Version hashes and unknown-type fallback; bound response bytes and avoid returning Source content. Compare against both the raw-buffer JS control and the current native persister. The measured mutable-heavy regression makes this the next processing task.
2. **Object-store inventory and batched reads.** Group existence checks, directory traversal, compressed-header classification and hash/content verification in Rust. Keep oversized Source content streaming; compare on both tmpfs and ordinary local disk. Preserve unreadable-object reporting, transformer hooks, permissions, cache identity and concurrent-file-change behavior. Measure warm commands as well as imports before adding a long-lived cache.
3. **Native mutable persistence and merge kernels.** Port Version, VersionHistory and LaneHistory merging with differential fixtures for parents, graph completeness, scope changes, duplicate histories and conflict/error policy. Port component merging and index construction once those primitives preserve the canonical behavior. Let Rust return a completed operation summary; avoid a callback to Node for every object or merge decision. Extension hooks need an explicit operation boundary and compatibility path.
4. **Tar-stream intake.** Move framing, entry traversal, Source validation and persistence together. Keep the existing authenticated HTTP client initially, feeding bounded chunks to Rust. Preserve `.BIT.START`/`.BIT.END`/`.BIT.ERROR`, schema handling, missing-end and truncated-tar errors, unknown members, cancellation and remote-error attribution. Buffer or spool bounded batches until JavaScript has made any required policy decisions; never acknowledge an incomplete import as complete. Qualify against Bit's original encoder/decoder and actual loopback HTTP route before deployment network tests.
5. **Distribution and platform qualification.** Package the object-import helper with source/runtime identity, target/ABI/license checks, integrity verification, atomic installation and rollback. Extend native metadata/rename behavior to Windows with real OS tests. Continue the exact pnpm Rust formatting/lint configuration. Keep generated archives, JSON, profiles and logs outside the source repository.
6. **Operation-level orchestration.** Once the kernels above are compatible, move queueing, index transactions and cacheable native state behind a Rust import operation. Compare complete user commands, not only native kernels. Extend beyond import to hashing, object traversal and component loading when the same operation boundaries reduce callbacks and improve measured command performance.

For every stage, commit small reviewable changes, target PRs to `rust-object-import`, preserve repository readback and canonical errors, and report whole-client CPU/memory including the helper. The existing four-mode command harness supplies the baseline. Native rollout stays opt-in until the broader workload/platform results justify the default; improving local processing does not remove network waiting.
